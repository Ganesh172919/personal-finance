# FinWise website and market-readiness audit

**Date:** 7 November 2026  
**Verdict:** Strong feature-rich local prototype; **not ready for a public launch, paid beta, or real-financial-data pilot in its present state**. A synthetic-data demonstration is reasonable. Fix the privacy, authentication, billing and financial-truth defects below before inviting real users; then validate a production-like deployment and a narrow consent-based pilot.

## 1. Scope, evidence and limits

This review covers the React/Vite website and its route journeys, Express API and worker, FastAPI AI Core, billing, deployment/CI and existing product documentation. The current working tree contains extensive **pre-existing uncommitted and untracked changes**, including an earlier 4 November audit; this report records the current working tree, not an audited release commit. No source or configuration was changed for this audit.

| Check run on this working tree | Result | What it does **not** establish |
| --- | --- | --- |
| `npm --prefix client test -- --reporter=dot` | **54 files / 451 tests passed** | Browser navigation, accessibility, external services or production hosting. Console output included expected negative-test errors and jsdom navigation warnings; the suite still passed. |
| `npm --prefix server run test:ci -- --reporter=dot` | **75 files / 326 tests passed** | Real payments, SMTP, OAuth provider, multi-replica behavior or live bank integration. |
| Client build and lint | **Passed**; Vite warned that the main JS chunk is **673.26 kB minified / 215.85 kB gzip** and exceeds the 500 kB warning threshold. | Mobile field performance without real-device measurements. |
| Server/worker production build | **Passed**; generated server and worker bundles. | Starting those bundles with production services and secrets. |
| `git diff --check` | **Failed** with pre-existing whitespace/EOF findings across the large worktree, including documentation and a changed PDF. | This is release hygiene, not evidence that the application tests failed. |
| AI Core pytest/evals; Docker Compose | **Not run**: the existing AI virtual-environment interpreter is broken, installed Python 3.15 lacks pytest, and the Docker CLI is unavailable. | Previous dated test counts in `docs/DEPLOYMENT_READINESS.md` are historical, not a new pass on today's tree. |

The audit is principally **source review plus local automated checks**. It did not start the full website in a browser, test a production URL, use real financial information, contact payment/bank/email/model providers, or verify legal compliance. Prior synthetic browser observations are documented in `docs/DEPLOYMENT_READINESS.md:135-158`; do not treat them as today's end-to-end results. Severity below reflects credible consequences from inspected paths, **not observed exploitation**. No complete audit can guarantee absence of further issues.

## 2. Product and website snapshot

The app has roughly 32 distinct lazy-loaded pages spanning authentication, private dashboard, transactions, finance, goals/debts, portfolio, analytics, files, chat, tasks, automation, calendar, billing, organization and public story sharing (`client/src/routes/routeDefinitions.tsx:84-135`). Its architecture is React → Express/MongoDB/GridFS plus a Mongo-polling worker → FastAPI/LangGraph AI Core. The best existing value loop is **record or import → review uncertain transaction → ask a source-linked question → save/complete an action → export a record** (`docs/PRODUCT_GOAL_AND_ACCEPTANCE.md:3-24`). Transaction approval is persisted against a hash of material values and reopens after a material change (`server/src/services/transactionReview.ts:247-265`); document Q&A and local deterministic answers provide a credible trust-oriented wedge.

**Do not market as:** live connected banking, real-time broker sync, independently fact-checked AI, genuine S3/GCS scheduled delivery, trained semantic embeddings, or established production reliability. The bank feed is a signed-in import simulator and cloud-storage delivery is unsupported (`AUDIT_REPORT_2026-11-04.md:23-29,57`; `docs/PRODUCT_CAPABILITY_STATUS.md:38-42`). Many 64-dimensional vectors are deterministic hashed/token features, not evidence of a trained embedding model (`server/src/services/retrievalService.ts:259-331`). Existing long-form documents sometimes describe aspirational capabilities as shipped; runtime code and dated tests are the authority.

## 3. Release blockers — fix before real users or paid access

**P0 = block public exposure/real-data pilot or paid launch.** The findings below identify code paths, scenarios and acceptance conditions, not just broad recommendations.

| ID | Finding and concrete failure scenario | Evidence | Required outcome |
| --- | --- | --- | --- |
| **P0-01: enabled 2FA can be bypassed at login** | A user enables TOTP, then anyone possessing only their password obtains a full JWT without an OTP; the Google callback also grants a full session. | `server/src/controllers/authController.ts:326-360,372-383`; setup enables the flag at `server/src/controllers/v1/twoFactorController.ts:101-112`. | Issue only a short-lived pre-2FA challenge after password/OAuth; require OTP or securely managed recovery code before issuing a normal JWT; test login, OAuth, replay, expiry and 2FA recovery. Until fixed, do **not** advertise effective account 2FA. |
| **P0-02: AI educational cache is shared across users despite personal prompts** | The first user's original question and profile goal names enter an LLM answer cached solely under a concept such as “budget”; a second user asking about that concept within the cache TTL can receive the first answer and any echoed private detail. | `server/AI_Core/agents/financial_educator.py:130-175,178-230`. | Disable this cache for personalized answers or key it by authorized user/org and all relevant inputs. Add two-user privacy regression and ensure invalidation on context changes. |
| **P0-03: AI canary health exposes unscoped financial inputs** | Authenticated users can run validation on their figures; the process-global recent-events list includes candidate/reference numbers and can be read by other authenticated users through the status endpoint. Node fallback has the same global-event shape. | `server/AI_Core/evals/canary_validator.py:106-132,408-419,650-702`; `server/src/services/aiCanaryService.ts:47-95,99-127`; `server/src/routes/v1Routes.ts:652-669`. | Return aggregate, non-sensitive health only to ordinary users; move detailed events to tenant/actor-scoped privileged storage or remove them. Test cross-user and cross-org read denial, including fallback mode. |
| **P0-04: paid credit packs require no payment** | An organization admin can POST a pack ID repeatedly; credits are granted immediately, and an audit event names the action a purchase without processor confirmation. The generated purchase ID is new each time. | `server/src/controllers/v1/billingController.ts:145-202`; `server/src/routes/v1Routes.ts:414-419`; `server/src/test/monetization.test.ts:76-103`. | Disable packs now; later grant only upon a verified, idempotent successful processor event, and test failed/refunded/replayed events. Never describe these grants as sales. |
| **P0-05: paid receipts and plan activation can be fabricated** | Reading an empty invoice list **writes** a `paid` invoice for an assumed Pro plan with “Card ending in 4242”; its PDF says “TAX INVOICE / RECEIPT” and “PAID.” Separately stub checkout activates paid plans and writes paid invoices without charging. Production selects stub by default when no Stripe key is set. | `server/src/controllers/v1/billingController.ts:205-245,277-316`; `server/src/services/billing.ts:113-155`; `server/src/config/env.ts:468-476`. | Remove invoice creation from GET. Generate invoices/receipts only from verified payment or explicitly labelled test records; render the actual status, issuer and jurisdictionally correct fields. In production, fail closed or disable monetization when the payment provider is missing; exercise real checkout/webhook/refund flows before charging. |
| **P0-06: financial guidance can use fabricated or misperiodized numbers** | With no forecast/history, “smart” caps default to hard-coded category averages, are described as based on actual expenditure and are preselected for saving. Separately AI sums a multi-month transaction window as `net_cash_flow`, calls it **monthly**, and the plan builder prefers that total as monthly cash flow; a 12-month surplus can be overstated 12×. | `client/src/pages/FinanceOS.tsx:499-557,588-605,1901-1911`; `server/AI_Core/agents/income_expense_analyzer.py:241-265,292-296`; `server/AI_Core/tools/plan_builder.py:188-211`. | Show “no history” or clearly labelled editable example amounts, never personalized averages. Compute month-specific or coverage-qualified monthly metrics; test 1/3/12-month and sparse periods, currencies, and the saved advice/action. |

## 4. Important issues before a wider pilot

**P1 = fix for a trustworthy limited pilot; P2 = prioritize after blockers or alongside UX hardening.**

| Priority / ID | Issue, impact and evidence | Next action |
| --- | --- | --- |
| **P1-01 / financial AI integrity** | The narrative number guard uses a set of unsigned, currency-stripped number tokens; changing a loss to a gain, swapping labeled values or changing a currency may pass. A generic AI exception becomes HTTP success with raw `str(e)`, fallback advice, request-context evidence and a failed session (`server/AI_Core/utils/agent_helpers.py:67-90`; `server/AI_Core/api_service.py:2405-2439`; `server/src/services/aiCoreClient.ts:738-755`). | Keep amounts, signs, currencies and labels in deterministic structured fields; forbid unsupported free-text transformations. Return explicit degraded/error status and safe messages; do not cache failures as successful evidenced advice; test provider outage and contradictory answers. |
| **P1-02 / active AI stream** | The client POST to `/ai/process/stream` sends a JWT cookie but no CSRF header (`client/src/services/aiStream.ts:25-35`), whereas cookie-authenticated mutations are CSRF-protected (`server/src/app.ts:388-394`; `server/src/middleware/csrfProtection.ts:64-85`). | Use the common API auth/CSRF/org header builder; test a real cookie-authenticated streaming request, cancellation and failure behavior. |
| **P1-03 / organization data access** | `/api/media/:fileId` checks the uploader's user ID but not current organization membership; a former member who uploaded a file and knows its ID can still retrieve it after losing access (`server/src/controllers/mediaController.ts:23-35`; `server/src/services/gridfs.ts:96-121`; `server/src/routes/mediaRoutes.ts:20-24`). | Require active org context/membership and match the file's org/purpose; regression-test revocation and workspace switching. |
| **P1-04 / broken invite and deep links** | `AcceptInvite` reads `?token=` from `useLocation()`'s path, not the URL search string; login/register `?next=` use the same pattern, and route guards can send authenticated users to dashboard before the redirect effect runs (`client/src/pages/AcceptInvite.tsx:40-49`; `client/src/pages/Login.tsx:53-84`; `client/src/routes/routeGuards.tsx:64-95`). | Read `window.location.search` (or the router's search API), preserve/validate return URLs and test invite → sign-in → accept, reload and deep link. |
| **P1-05 / tablet navigation gap** | Desktop sidebar is hidden below 1024px but the mobile bar/drawer only appears below 768px: at widths 768–1023px neither primary navigation exists (`client/src/components/Sidebar.tsx:309-311,521-538`; `client/src/hooks/use-mobile.ts:26-51`). | Align breakpoints or provide a tablet menu; test widths 767/768/1023/1024px with keyboard and touch. |
| **P1-06 / silent CSV data loss** | Onboarding slices a parsed statement to its first 500 rows and imports only those rows, without explaining that additional rows were discarded (`client/src/pages/Onboarding.tsx:307-331,353-388`). | Explicitly count, preview, map and import all supported rows in bounded batches, or block oversize imports with a clear action; test >500 rows and deduplication. |
| **P1-07 / production verification gaps** | Docker is unavailable here; production Compose startup, HTTPS/cookies, worker drain and multi-replica idempotency are not verified. The CI workflow runs tests/build/lint, not a Compose smoke or restore drill (`.github/workflows/test.yml:20-154`; `docs/DEPLOYMENT_READINESS.md:156-180`). | CI/staging: build Compose, run readiness and synthetic signup/import/AI/worker/export paths, restore a backup, exercise shutdown/failover and record a release SHA. |
| **P1-08 / email and scheduled jobs** | Production email throws without SMTP; registration persists an unverified user before email delivery, so a template-based deployment may leave signup failed with a reserved address (`server/src/utils/sendEmail.ts:145-150`; `server/src/controllers/authController.ts:137-155`). Newsletter scheduling starts per web replica with process-local deduplication (`server/src/server.ts:257-260`; `server/src/services/newsletterScheduler.ts:138-149,180-195`). | Validate SMTP/delivery and recovery before signup; run a single elected scheduler or durable idempotent send jobs with recipient/period keys. |
| **P1-09 / paid-plan contract** | Credit grants are keyed to a monthly period while the UI promises non-expiring, automatically rolling-over boosters (`server/src/services/credits.ts:22-26,41-74`; `client/src/pages/Billing.tsx:823-835,918-920`). Stripe selects the same price IDs regardless of monthly/annual toggle; Team quantity is seats (`server/src/services/billing.ts:107-111,157-160,185-210`). | Reconcile entitlements, rollover, checkout currency, annual price IDs, seat units, refunds and receipts with displayed terms; run processor sandbox tests and legal review. |
| **P2-01 / false empty states** | Finance accounts and transactions can show “No accounts yet” / “No transactions found” on fetch failure instead of distinguishing unavailable data (`client/src/pages/FinanceOS.tsx:749-797`; `client/src/pages/Transactions.tsx:240-252,1733-1753`). | Show error + retry separately from genuinely empty data, especially for balances and ledger; test 503/429/offline and recovery. |
| **P2-02 / misleading financial story** | “Overall Financial Health” is only goal funding; “Milestones Achieved” counts AI insights; “Total Assets” adds profile savings and goal balances, possibly double-counting (`client/src/pages/FinancialStory.tsx:125-135,172-195`). | Relabel to actual measures and explain completeness, or compute reconciled net worth and real milestone completion. |
| **P2-03 / keyboard accessibility** | Mobile drawer has visual overlay but lacks dialog semantics, Escape behavior and focus containment (`client/src/components/Sidebar.tsx:385-460`). | Use an accessible dialog/sheet and test keyboard, focus return, labels, screen reader and reduced motion. |
| **P2-04 / mobile performance, discovery and documentation** | The entry JS is 673.26 kB minified; hidden Finance tabs initiate multiple queries (`client/src/pages/FinanceOS.tsx:235-460`). Public educational discovery is limited: blogs/stories/docs require auth and static HTML metadata is shared (`client/src/routes/routeDefinitions.tsx:123-130`; `client/index.html:9-13`). Several older documents overclaim BullMQ, production AI safety, bank ingestion or cloud upload (`docs/PRODUCT_CAPABILITY_STATUS.md:3-6,30,35-42`). | Gate tab queries, set Web Vitals budgets, and test on low-end phones. If organic search is a channel, publish deliberate public-safe educational pages with per-page metadata/prerendering; keep private URLs out of search. Make one verified capability matrix and label design-only material. |

**Operational/privacy follow-up:** Authentication logs include complete email addresses (`server/src/controllers/authController.ts:129,187,293,375`); reduce identifier exposure and define retention/access. The dead-letter list is process-local rather than a durable replay queue (`server/src/services/deadLetterQueue.ts:88-106,131-158`), so document actual recovery guarantees. Review data deletion, consent, sharing, encryption, backup retention, jurisdictional advice and receipt language with counsel before real-data distribution; this audit is **not** a legal certification.

## 5. Go-to-market recommendation

### Who to serve first and what to say

**First cohort (hypothesis):** privacy-conscious, CSV/spreadsheet-comfortable individuals or households who already have their own statement records and want to reconcile spending, bills, budgets and debt. These users can reach value without a live bank connector. The proposed offer is **“Turn your financial records into a reviewed ledger, source-linked answers, and one concrete next action.”** Prove the loop in supervised interviews before expanding to teams, brokers, banking automation or autonomous investing. No traffic, revenue, retention or willingness-to-pay data was found in this repository.

**Why this might matter, not evidence of product-market fit:** The [Federal Reserve's 2025 household survey, published in 2026](https://www.federalreserve.gov/publications/2026-economic-well-being-of-us-households-in-2025-savings-investments.htm) reports limited emergency savings for many US adults; the [CFPB's 2024 Making Ends Meet survey](https://www.consumerfinance.gov/data-research/research-reports/making-ends-meet-in-2024-insights-from-the-making-ends-meet-survey/) describes bill-payment pressure. Those are population signals, **not** a FinWise market size, customer conversion estimate, competitor comparison or verified demand. Validate country, audience and regulation before geographic targeting.

| Stage | Offer and distribution | Gate to next stage |
| --- | --- | --- |
| **0. Synthetic demo (now)** | Demonstrate a clearly synthetic import → review → cited document answer → task → export. Invite feedback, not sensitive data or payment. Avoid false claims of live integrations, autonomous advice or real receipts. | Blockers assigned, reproducible demo and honest copy. |
| **1. Private real-data pilot (after P0/P1 trust fixes)** | Recruit a small consented CSV-first cohort directly through interviews or relevant finance/product communities; support each first import and measure errors. Publish clear security/privacy, limitations, export/deletion and support information. | 2FA and tenant privacy regressions; payment routes disabled; clean staging, restore and SMTP checks; owner-approved privacy/legal review; successful desktop/mobile/keyboard journey. |
| **2. Free public core (after pilot evidence)** | Give a useful manual/CSV ledger, review and a basic data export; consider public educational pages only if search acquisition is chosen. Do not charge before billing integrity is fixed. | Activation, repeat use, incident rates, cost and support thresholds set in advance and met on staging/pilot. |
| **3. Paid Pro, then Team** | Experiment with cited document Q&A, higher quotas, automation and reports as premium value; test pricing by interviews/controlled offers, not assumed willingness to pay. Add Team only when collaboration and access revocation are proven. | Verified Stripe checkout/webhooks/refunds, interval/seat/currency contract, honest invoices and credit accounting, tax/legal review, measured margins. |

The current Free catalog has `export_access: false` (`server/src/services/entitlements.ts:163-185`), but keeping a copy is part of the stated first-session outcome (`docs/PRODUCT_GOAL_AND_ACCEPTANCE.md:9-24`). **Recommendation:** allow a basic, bounded personal CSV export on Free; monetize advanced scheduled/report delivery instead. In-app Pro/Team prices are hypotheses, not observed revenue (`client/src/pages/Billing.tsx:575-600,663-805`).

### Value to add, in order

1. **Reduce time to first value:** after verification, offer a three-step checklist (enter/import with preview, approve one uncertain row, view one trustworthy insight). Verification currently defaults to dashboard (`client/src/pages/VerifyEmail.tsx:87-103`), while onboarding is a separate route (`client/src/routes/routeDefinitions.tsx:109-123`). Defer optional risk-profile questions until they unlock an actual action.
2. **Make trust visible:** original-currency/source markers, missing-data warnings, exact physical document page links, plain-language calculation assumptions, a visible “not advice / not a live balance” boundary, and an easy correction path. Do not present similarity or canary status as independent factual verification.
3. **Close the loop:** move a reviewed anomaly or cited recommendation into an editable task, then show completion and a clean export; measure successful actions, not number of dashboards or agents.
4. **Control AI cost and failure:** prefer deterministic calculations/quotations for narrow questions, add provider-price ceilings and verified fallback labels, measure cost per **useful answer** and document job, and keep private telemetry free of raw finance content. Catalogue prices can default to zero (`server/AI_Core/utils/model_catalog.py:199-225`), so reported spend needs verification.
5. **Earn retention before breadth:** weekly review digest with idempotent delivery, forecast accuracy feedback, data-portability controls and accessible mobile journeys. Avoid building more large feature cockpits before the core journey is reliable.

### Proposed measurement contract (targets to set, not achieved results)

Track **invited → verified → first import/entry → first durable review → first source-opened answer or grounded insight → task saved/completed → export** by consented workspace. Track median/p95 time to each step, four-week repeat completion of the loop, corrected/import-dropped rows, citation-page accuracy, wrong-amount/currency incidents, 2FA enforcement, cross-tenant tests, error/retry success, mobile Web Vitals, AI fallback rate/cost/latency, support tickets per active workspace, and actual processor-confirmed paid conversion. Instrument event metadata only—never raw statements, prompts, personal goal text, cookies, payment credentials or private canary figures. Define release thresholds and ownership before collecting pilot data (`docs/PRODUCT_GOAL_AND_ACCEPTANCE.md:26-32`).

## 6. Suggested action plan and release gates

| Timing / owner | Work package | Acceptance test / exit criterion |
| --- | --- | --- |
| **Immediate — backend/security** | Enforce 2FA; block paymentless credit grants, stub activation and fabricated invoices; scope media; remove cross-user educational cache and canary details. | Negative two-user/two-org regression; enabled-2FA login cannot issue a JWT without OTP; unpaid/refunded/replayed payment events never mint entitlement or receipts. |
| **Immediate — finance/AI** | Remove fabricated caps; correct monthly-period math; preserve sign/currency/field semantics; make degraded AI status explicit. | Synthetic 1-, 3- and 12-month fixtures; no-history screen creates no “historical” cap; failure returns no successful evidenced advice. |
| **Next — frontend/product** | Fix invite/query return paths, tablet menu and CSV truncation; add retryable financial error states and accessible drawer. | Browser E2E on a clean staging account at phone/tablet/desktop sizes; >500-row import total and signed cents reconcile; invitation works through auth. |
| **Next — release/operations** | Enable SMTP and recovery, compile/start API and worker with production-like env, run Compose smoke and backup/restore, review secrets/TLS/CSRF/PWA; resolve pre-existing dirty diff and doc drift. | Clean reviewed release SHA; CI client/server/AI tests + container health + representative browser flow + worker and restore drill pass. |
| **After trust gate — product/market** | Run 1:1 first-session interviews, test CSV-first messaging and free portability; then payment sandbox, legal review and limited paid experiment. | Actual activation/retention and processor-confirmed revenue evidence, published support/privacy terms and predefined quality/cost thresholds. |

**Go/no-go:** Until the P0 items and staging gates are resolved, show only a synthetic demo. Do not ask users to connect bank data, upload real sensitive documents, enable 2FA as a promised protection, or pay for a plan/credit pack. A green local unit suite is an encouraging engineering signal, **not** a production approval.
